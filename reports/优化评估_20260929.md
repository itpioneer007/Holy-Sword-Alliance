## 三、五个断点（按影响排序）

### 环 1 — 守护：看门狗每天都会过期【最紧急】

**实测证据**（`Get-ScheduledTask SJBot_Console_Guard`）：

```
State         = Ready
LastRun       = 09/26/2026 20:30:01
LastResult    = 3221225786  (0xC000013A = STATUS_CONTROL_C_EXIT)
NextRun       = (空)
Triggers      = 1
  StartBoundary = 2026-09-22T17:50:00
  EndBoundary   = 2026-09-22T20:31:12      <<< 已过期 7 天
  Repetition    = PT10M / Duration PT2H40M
```

**根因在源码里，而且脚本自己知道**：`scripts/install_console_task.py:126`

```python
end = at + timedelta(hours=hours) + timedelta(minutes=1)
```

`build_xml()` 把 `EndBoundary` 设成"安装时刻 + hours 小时 + 1 分钟"。该函数 docstring（第 117 行）原文写着：

> "EndBoundary 卡在当晚: 触发器的活动窗口只覆盖今天这一段, 明天不再响。"

**已知未修 ⇒ 每次安装只能护住一次窗口，之后永久失效。**

当日症状：`netstat` 无 5050 监听，控制台连续 3 天（09-27 ~ 09-29）没有守护介入（`console_guard.log` 最后一条是 09-26 19:50:07）；09-28 20:02 那次任务实例结束后控制台随之死亡，无人拉起。

**修法（一处一行）**：`<CalendarTrigger>` + `<ScheduleByDay><DaysInterval>1</DaysInterval>` 组合下，`<EndBoundary>` 是**可选元素**，直接删除即可让触发器永久按日重复；同时补一个 `<BootTrigger>` / `<LogonTrigger>` 覆盖重启场景。改完装一次，之后不用再管。

### 环 2 — 预约：每天都要人登记

**实测**：`data/schedule.json` → `{"items": {}, "last": {...}}`，**当前预约列表为空**。今晚 18:00 无任何预约。

设计上"预约仅当日有效"（目标日 23:59 为界）是合理的防僵尸措施，但副作用是**每天都必须手动登记一次** —— 与"人不在也能开打"直接冲突：人不在，谁登记？

**修法**：把"每日 18:00 rank_glory / 周六日 16:00 arena"做成**常驻规则**而非当日一次性条目。两种落法：
- 服务端：`JobScheduler` 支持 `rrule` 式周期条目，`items` 里存规则而不是日期；
- 客户端：用系统级定时任务每天 17:55 调 `POST /api/jobs/schedule` 登记当日条目（改动最小，不动后端）。

### 环 3 — 重试：异常终止后没有任何自动续跑

**实测**：`grep -n "重下发|reschedule|retry|auto_restart|last_fail" sj_bot/server.py` → **零命中**。`JobScheduler`（`server.py:382`）只做"到点下发"，没有"失败后冷却重下发"。

**影响面**：
- 09-22 白丢 44 分钟（已由环 1 的窗口感知自愈部分覆盖）
- **09-27 12:37 `nav_failed` / fought=0** —— 一局没打就终止，当天剩余时段全部浪费
- **09-28 12:10 `stopped` / fought=0** —— 同样零产出

**修法**：任务收尾时判断原因，落在"非正常原因"（排除 `window_closed` / `daily_limit` / `finished` / 人工 `stopped`）且窗口仍开、且当日重下发次数 < N 时，冷却 60s 自动重下发。这是 09-22 遗留的第 ② 条建议，成本低、收益直接。

### 环 4 — 告警：异常终止无人知晓

**实测**：`grep -rn "notify|webhook|smtp|sendmail|bark|ServerChan|pushplus"` 在 `sj_bot/*.py` **零命中**。项目内置了完整的终止原因体系（`JOB_REASON` / `reason_info()` / `enrich_result()`），但这些信息只呈现在浏览器页面上，**没有任何主动推送通道**。

后果：所有异常都是"下次人来看的时候才发现"，而窗口是一次性的、过期不候。

**修法**：任务收尾时把 `enrich_result()` 的摘要 POST 到 webhook（Bark / 邮件 / Server 酱任选），**只在异常原因时推送**，正常收尾静默。这是投入产出比最高的一项。

### 环 5 — 复盘：日志重启即失忆（也是本次评估的硬约束）

**实测**：
- `sj_bot/server.py:1011` `api_logs()` 走 `LOG.lines(after_seq=...)`，是**内存环形缓冲**；
- `sj_bot/botlog.py` 全文（49 行）**没有任何文件写入**；
- `grep -rn "冻结" sj_bot/ web/` → 仅命中一个无关注释 ⇒ `reports/*运行日志冻结*.txt` **是人工产物，没有自动导出**。

**直接后果（本次亲历）**：`reports/` 目录最新一份日志冻结停在 09-23；09-24 ~ 09-28 六天的运行日志**全部不存在**。因此我**无法诊断 09-28 13:45 那场 19 局 4 胜 15 负（21% 胜率）** —— 这是全月最差的一场，但没有任何过程数据可回溯。

**修法**：给 `LOG` 加一个 append-only 文件 sink（按日轮转，如 `data/logs/2026-09-29.log`），`/api/logs` 启动时从当日文件回填。改动小，但它把"可诊断性"从"靠运气"变成"默认具备"。

## 四、第二梯队：正确性与数据异常

### 4.1 自愈额度：09-22 的根因**已修完**，但 `rank` 的"连续 3 次"上限仍是残余风险

**先纠正一个容易误判的点：`_selfheal_progress()` 不是清零的地方。**

```python
# battler.py:1521-1523
def _selfheal_progress(self) -> None:
    """本局已确认进入战斗页/结算链 = 有进展 -> 重置"窗口内无进展"计时。"""
    self._selfheal_since = None      # 只清 stall 计时, 有意为之
```

真正清零点在**每完成一局**处，`battler.py:2855-2865`：

```python
            # ---- 完成一局, 计数 ----
            self.fought += 1
            # 本局走完 = 这一族的自愈成功了: 各族计数归零, 让日志里的"第 N 次"与退避秒数
            # 反映的是**连续**自愈次数, 而不是整个任务期间的累计次数。
            # (2026-09-22: 累计语义下, 一晚每次都被自愈救回也会把计数推到上限 —— 那正是
            #  18:42 被冤枉终止的成因之一; 连续语义才不会误伤正常的长时段挂机。)
            self.match_rescues = 0
            self.nav_rescues = 0
            self.game_rescues = 0
            self.session_rescues = 0
            self.main_city_rescues = 0
```

**结论：09-22 的根因修复是完整且正确的。** 语义已从"任务级累计"改为"连续计数"，五族齐全。这一点无需再动。

残余风险在 `battler.py:1474-1475`：

```python
        jt = self._mode_window()
        if jt is None:
            return "cap" if streak > SELFHEAL_LEGACY_MAX else "go"   # rank 走这里
```

- **荣耀 / 争霸**（有窗口）：`cap` 永不触发，只受窗口与 15min 无进展约束 ⇒ 修复有效 ✔
- **日常排位 rank**（无窗口）：仍是**连续 3 次自愈未打成一局 → 终止**

在 ~7 分钟一次进程回收的压力下，"连续 3 次回收都来不及完成一局"（每次要重启 + 登录 + 导航，冷启动 12~15s 起）在理论上是可发生的。`SELFHEAL_LEGACY_MAX=3` 对 rank 可能偏紧。

**但必须说明：我没有证据认定 09-27 的两次 rank 异常终止（`nav_failed` / `no_battle_ui`）就是这个原因** —— 那两天的日志未落盘（见环 5），无法回溯。**因此建议先补日志取证，再决定是否把 rank 也切到窗口/进展语义**，不要再凭推测改阈值。

### 4.2 `nav_failed` 零局终止值得单独查

09-27 12:37 `nav_failed` / fought=0 —— 启动即失败，一局未打。当天 `captures/` 有 7 张异常图（`antibot_first` ×2、`main_city_rescue1/2` ×2 组），时间集中在 13:58~15:03，**说明 12:37 那次连现场图都没留下**。建议：导航入口失败时增加"重截一帧 + 二次判定"再决定收尾，并强制留图。

### 4.3 `main_city_loop` 在窗口末尾反复出现

新增落码（`server.py:84`，注释："多为防挂机弹窗期间匹配倒计时归零"）。09-24 与 09-28 各在 **20:02（窗口末尾）** 触发一次，说明防挂机弹窗悬停期间匹配倒计时归零是稳定复现的行为模式。既然它总在窗口末尾出现且不影响本场结果，可考虑在该场景下**不计入异常**，减少噪音。

### 4.4 09-28 那场 21% 胜率是数据异常

19 局 4 胜 15 负，对比同期：09-24 荣耀 65%、09-28 荣耀 52%、09-27 排位 47%。偏离幅度大，可能是"匹配到强对手 / 点错按钮 / 战斗页判据误判导致跳过时机错"。**但受环 5 阻断，无日志无样本，无法定论。**

### 4.5 web 控制台看不到异常截图

`server.py` 无 anomaly 相关端点（`grep` 零命中），异常图只落在 `captures/`。诊断时必须上盘翻文件名，而 `captures/` 还有 71MB、无保留策略。建议加一个只读端点 + 缩略图列表。

## 五、第三梯队：工程卫生（风险最高的一项其实在这里）

### 5.1 项目不是 git 仓库 —— 无版本控制

```
$ git status
fatal: not a git repository (or any of the parent directories): .git
```

现状是**手工备份**：`sj_bot/battler.py.bak-20260923-menu`、`sj_bot.bak-20260911-rules/`、`data/*.bak-2026091x`、`web/index.html.bak-20260911`……

**这是全项目风险最高的单点**：`battler.py` 3084 行 + `server.py` 1050 行，改错一处无从回滚、无法 bisect、无法比较两个版本的分歧。所有"先备份再改"的规矩都是在替代 git。

**建议**：`git init` + 首个 commit + 把 `captures/`、`data/*.db*`、`*.bak-*` 写进 `.gitignore`。半小时的事，收益是永久性的。

### 5.2 无统一测试入口，且一个自测长期处于崩溃状态

- `scripts/` 下 **58 个 .py**，没有任何 `run_all_*` / `test_all_*` 入口；
- `nav_retry_selftest.py` 依赖 `captures/_p3_*.png`，而 `captures/` 有例行清理 ⇒ **09-23 已因此崩过一次**，至今未恢复（当前 `captures/` 只剩 37 张 anomaly 图，样本早没了）。

**建议**：① 建 `scripts/run_all_selftest.py` 统一跑全部 `*_selftest` 并汇总；② 长期回归样本一律放 `assets/*_ref/`，脚本内用 `np.fromfile + imdecode` 读（这条规约 09-23 已确立，但 `nav_retry_selftest` 还没迁）。

### 5.3 `captures/` 71MB 无保留策略

只增不减。建议启动时或每日清理超过 N 天的异常图，或按"每月保留 X 张"归档。

### 5.4 `battler.py` 3084 行单文件

页面分类、战斗判定、结算链、自愈、防挂机、导航全在一个类里。改动风险高、测试难隔离。建议按职责拆成 mixin 或子模块（如 `page_classify.py` / `battle_flow.py` / `selfheal.py`），**但这项收益是长期的、且改动面大，建议排在 git 之后**。
