## 四、18:42 异常终止根因

**根因 = 模拟器反复回收游戏进程 + "会话失效自愈"额度是任务级累计、恢复成功也不退还。**

关键日志（`reports/..._运行日志冻结.txt`）：
```
18:41:57 [warn ] 等待比赛界面超时, 页面识别: unknown (自愈 1/3)
18:41:59 [warn ] 逃生(match_timeout): 无法识别的真实原因是游戏不在前台, 先拉起游戏
18:41:59 [warn ] 游戏进程已不存在 (被模拟器回收?), 重新拉起游戏 (tag=escape_match_timeout)
18:42:14 [warn ] 逃生(match_timeout) 拉起游戏后页面识别: login
18:42:14 [error] 会话失效自愈已达上限 (>3), 任务终止 (请人工登录一次)
18:42:14 [info ] 任务结束(no_battle_ui): 打 19 场 = 胜 7 / 负 11 / ...
```
额度消耗轨迹（**跨 3 次成功恢复累计**，这是要害）：
```
18:17:03 -> 尝试重新登录并重导航 (1/3)   之后成功续打 12 场
18:23:14 -> 尝试重新登录并重导航 (2/3)   之后成功续打  8 场
18:36:16 -> 尝试重新登录并重导航 (3/3)   之后成功续打  3 场
18:42:14 -> 已达上限 (>3)                -> 终止
```
即：**前三次自愈都是成功的**（拉起→落在 login→重新登录→重新导航→继续打），但计数器不退还款，第 4 次回收就把整场窗口的额度打光。诱因是环境性的（本机可用内存约 2 GB，MuMu 反复回收 `com.holyblade.sjlm.ganxt`），但"成功后不回滚"是设计缺陷。

### 修复建议（按优先级）

1. **自愈额度按"事故"而非"任务"计数**：一次完整恢复（重登录 + 重导航成功、且后续成功打完一局）后退还额度，或把上限从 3 提到与"回收频率 × 窗口时长"匹配的量级（今晚节律约 7 分钟一次 ⇒ 120 分钟窗口需要 ≥15 次额度）。
2. **窗口内异常终止自动重下发**：`JobScheduler` 目前预约只下发一次，任务死了就没人接手（今晚白丢 44 分钟）。建议加"窗口内异常终止 → 冷却 60s → 自动重新 start，累计上限 3 次"，可把这类损失从 44 分钟压到 ~1 分钟。
3. **降内存压力**：给 MuMu 提高内存上限 / 关掉后台其它程序，直接降低游戏被回收的频率——这是诱因层的根本解。
4. **（次要）登录态**：每次拉起都停在 login，若能缩短冷启动登录耗时，也能省额度。
